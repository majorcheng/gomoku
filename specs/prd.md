# 产品需求文档 (PRD): Web 五子棋对弈系统（自研引擎）

## 1. 项目概述

* **项目名称**：Gomoku（纯前端 Web 五子棋，自研 Alpha-Beta + VCF 引擎）
* **定位**：零后端、零第三方依赖、可直接托管在 GitHub Pages 的现代化五子棋对弈应用。
* **核心亮点**：
  * **完全自研引擎**：不依赖 Stockfish/任何第三方棋力库。迭代加深 Negamax
    Alpha-Beta + Zobrist 置换表 + 杀手/历史启发 + **VCF 连续冲四算杀**，
    全部跑在 Web Worker 里，主线程零卡顿。
  * **零依赖、零下载**：整个应用无构建步骤、无 CDN、无 wasm、无字体文件，
    首屏直接加载源码。相比 02.chess / 03.chess_master 的
    数十 MB 引擎产物，这是本系列最轻量的一个。
  * **权威规则判定**：落子合法性、禁手、五连/长连获胜、棋盘满和棋由主线程 `rules.js`
    判定；侧栏的深度/节点/NPS/耗时/分数全部来自引擎真实搜索输出，不做任何编造。
  * **难度如实标注**：低难度走了非引擎首选的落子时，侧栏明确标注「次优」，
    不伪装成最优（沿用 03.chess_master 的诚信原则）。

## 2. 技术架构与分层

沿用系列的「**视图 UI - 业务裁判 - 算力引擎**」三层解耦：

```text
+-----------------------------------------------------------+
|                    Web UI (视图层)                          |
|  Canvas 30×30 棋盘渲染/点击/悬停预览 + 模块化 CSS            |
+----------------------------+------------------------------+
|                 业务裁判层 (主线程)                          |
|  rules.js 禁手、落子合法性与五连判定                         |
|  difficulty.js 档位定义与落子采样（难度单一事实来源）          |
|  engines/bridge.js 引擎门面 (load/search/cancel/status)     |
+----------------------------+------------------------------+
|          自研五子棋引擎 (Web Worker)                         |
|  - 迭代加深 Negamax α-β（时间上限 + 深度上限双保险）          |
|  - Zobrist 置换表 + 杀手启发 + 历史启发                      |
|  - VCF 威胁空间搜索（连续冲四算杀）                           |
|  - 点评估模式打分：活四/冲四/活三/眠三/活二… 经典棋型表        |
|  - 根节点硬规则：己方能五连必走、对方五连必挡（任何档位生效）   |
+-----------------------------------------------------------+
```

### 2.1 为什么不用现成引擎

调研结论（见 README 的调研记录）：

1. 五子棋没有 Stockfish 这样的官方 WASM 构建，强引擎（Gomocup 级 C++ 代码）
   需要 Emscripten 交叉编译，维护成本高于自研；
2. Alpha-Beta + 启发式评估 + VCF 的组合在 15×15 上调好参数后棋力已远超普通
   人类玩家（研究结论：6-8 层有效深度即超过休闲玩家），JS 性能足够；
3. AlphaZero 路线训练成本高（8×8 棋盘要自对弈 2000-3000 局），且与
   「纯静态、即开即玩」的部署目标冲突。

自研引擎因此成为本系列里**唯一完全自有知识产权**的一个（MIT 许可即可，
无需 GPL 传染）。

### 2.2 棋盘与走子表示

* 30×30，一维 `Int8Array(900)`：`0` 空、`1` 黑、`2` 白。
* 坐标记法：列 `A..AD`（左→右）、行 `1..30`（下→上）。
  偶数边长没有唯一天元，默认开局取中央四点的右下点 `P15`（index 465）。
* 主线程与 Worker 各持一份棋盘；Worker 每次搜索收到**完整着法序列**并重放
  （最多 900 步），避免增量同步的状态漂移 bug。

## 3. 规则集

**30×30 棋盘沿用连珠禁手规则**：

| 项 | 规则 |
|---|---|
| 棋盘 | 30×30 |
| 先行 | 黑先行，轮流落子于任意空交叉点 |
| 胜利 | 黑方形成恰好五连，或白方形成五连及以上，先完成者获胜 |
| 和棋 | 900 个交叉点全部落满仍未分出胜负 |
| 禁手 | 黑方的长连、双三、双四均为禁手；白方无禁手 |

> 主线程与 module Worker 直接复用 `rules.js`。黑方恰五优先；跳活三的延伸必须合法，
> 假活三按递归判例排除。根候选、内部搜索和 VCF 攻防都遵守同一裁判。

## 4. 引擎设计（核心）

### 4.1 评估函数：点评估 + 棋型表

对任一空点 `p` 与颜色 `c`，`scorePoint(p, c)` = 假设在 `p` 落 `c` 子后，
四个方向形成的棋型分之和。棋型分（黑双方同表）：

| 棋型 | 记号 | 分值 | 含义 |
|---|---|---|---|
| 五连/长连 | FIVE | 10,000,000 | 白方直接获胜；黑方由裁判确认恰五 |
| 活四 | OPEN_FOUR | 1,000,000 | 两端皆空，下一手必胜 |
| 冲四 | FOUR | 100,000 | 一端成五，逼迫对方应 |
| 活三 | OPEN_THREE | 90,000 | 下一手可成活四 |
| 眠三 | THREE | 3,000 | 跳/断三，潜在冲四材料 |
| 活二 | OPEN_TWO | 2,500 | 潜力型 |
| 眠二 | TWO | 300 | |
| 活一 | ONE | 30 | |

> 活三与冲四同量级（90k vs 100k）是有意的：双活三 ≈ 活四级别威胁，
> 让搜索自然优先处理连续威胁局面。终局分 `WIN = 10,000,000 - ply`
> （越快获胜分越高，引导最短杀）。

静态评估 = 黑方全部棋型分 − 白方全部棋型分，再转换为行棋方视角；对手棋子隔开的
片段独立计分，旧线分缓存。静态分不跨越胜负阈值，胜负分由合法成五或强制变化证明。
高级及以上在基础两层后，对仍有强制变化的叶子额外延伸最多 4 手。

### 4.2 候选点生成与排序（搜索效率的生命线）

* 候选 = 已有棋子 **切比雪夫距离 ≤ 2** 内的空点；空盘直接返回 `P15`。
* 每个候选按 `scorePoint(p, 自己) + scorePoint(p, 对方) × 0.9` 降序排序
  （进攻 1.0 / 防守 0.9 的混合权重）。合法的一步赢、必挡在启发式排序之前处理。
* 普通候选浅层取前 `candWidth` 个合法着法（12~32），深层 `max(8, candWidth / 2)`；
  高级及以上保留全部真实冲四，数量可超出普通宽度。禁手不占限额。
* 点评分缓存仅在落/撤点四方向各四格内失效；稳定有界插入排序只保留前 K 项。

### 4.3 搜索框架

```text
go(moves, level):
  1. 重放着法序列
  2. 硬规则①：己方能合法成五 → 立即返回
  3. 硬规则②：对方能合法成五 → 优先合法挡点，非法挡点不参与搜索
  4. 完成基础搜索后，以有限子预算运行 VCF（只尝试真正产生合法成五点的冲四），
     找到必胜 → 返回，标记 vcf=true
  5. 迭代加深 Negamax α-β：
     - 每层结束上报 info{depth, score, nodes, time, pv}（真实数据）
     - Zobrist 置换表（32 位双键校验，深度/标志/分数/最佳着法）
     - 杀手启发（每层 2 个）+ 历史启发（按 β 截断次数衰减）
     - 时间上限与深度上限先到者停（与 Stockfish go depth + movetime 同语义）
     - 高级及以上叶子延伸最多 4 手强制变化，仍受总 deadline 约束
  6. 根节点按难度档位采样（difficulty.pickMove）
```

### 4.4 VCF（Victory by Continuous Fours）

* 攻方**只**尝试能形成冲四/活四的落子；防方唯一合理应手是挡五点
  （防方若有自身五连则直接反杀，剪枝返回）。
* 深度上限 20 层 + 节点预算上限 200,000；子预算 `min(400 ms, 剩余时间 × 20%)`。
  子预算耗尽只退出 VCF，普通搜索继续；两者都受整手总预算约束。
* 递归退出通过 finally 撤子；超时后不混排不同深度的分数，保留最近完整层。
* 命中即返回 `WIN - ply` 分与杀法路线；侧栏标注「VCF」来源，
  不与普通搜索的结果混淆。

### 4.5 性能预算（2026-09-12 Node 实测回写）

以下为旧 15×15 棋盘的历史数据；30×30 固定局面基准和算法取舍见
[README_CN.md](../README_CN.md#30×30-搜索加速与算法参考)，未重新标定整套难度胜率。

| 档位 | 深度 | 时间上限 | 实测单步耗时 | NPS |
|---|---|---|---|---|
| 1 入门 | 1 | 200 ms | ~1 ms | ~9k |
| 2 初级 | 2 | 500 ms | ~2 ms | ~19k |
| 3 中级 | 4 | 1,000 ms | ~30 ms | ~15k |
| 4 高级 | 6 | 1,500 ms | 0.3~0.7 s（自对局均值） | ~31k |
| 5 大师 | 8 | 2,500 ms | ~1-2.5 s | ~43k |
| 6 宗师 | 12 | 4,000 ms | ~2-4 s | ~110k |

> 实测平台 Node 22（V8）。浏览器 Worker 同引擎同 V8 量级。
> 深度列是上限——搜索在必胜分（±9M）出现、时限或候选耗尽时提前停止，
> 实际深度常低于上限。校准对局（相邻档位机机对战）结果回写在
> `js/difficulty.js` 头部注释：无档位倒挂。

## 5. 难度分级设计

**两级旋钮**（与 03.chess_master 的思路同构，但全部作用于自研引擎）：

1. **搜索弱化**：深度上限、时间上限、候选宽度——控制「能看多远」；
2. **根节点采样**：softmax 温度 + 失误率——控制「看准了会不会走歪」。

**不可弱化的硬底线**（所有档位一律生效，防止「看起来像 bug」）：

* 己方合法一步成五 → 必走（搜索中已排除黑方禁手）；
* 对方一步成五 → 必挡（含以冲四反杀的选项，交给搜索比较）；
* 采样带**损失上限**：候选分差超过档位上限时强制回引擎首选。

### 六档定义

| 档 | 名称 | 深度 | 时限 | 候选宽 | 温度 | 失误率 | 目标棋力 |
|:--:|:--:|---|---|---|---|---|---|
| 1 | 入门 | 1 | 200 ms | 12 | 500k | 0.30 | 刚学会的人 |
| 2 | 初级 | 2 | 500 ms | 16 | 300k | 0.12 | 休闲玩家 |
| 3 | 中级 | 4 | 1,000 ms | 20 | 120k | 0.02 | 有基本攻防意识 |
| 4 | 高级 | 6 | 1,500 ms | 24 | 60k | 0 | 业余中等 |
| 5 | 大师 | 8 | 2,500 ms | 32 | 0 | 0 | 业余强手 |
| 6 | 宗师 | 12 | 4,000 ms | 32 | 0 | 0 | 引擎全力 |

档位参数以 `js/difficulty.js` 为**单一事实来源**，主线程与 Worker 都从它读。
温度单位是**评估分**（非厘分，量级见 §4.1 棋型表）。

> 档位数值是待校准初值，实现完成后用「机机对战」（相邻档位各若干局、
> 先后手互换）校准并回写注释。

## 6. 引擎通信协议

`engines/engine.worker.js` 是**纯消息协议**的 Worker（不依赖任何全局）：

**主线程 → Worker**
```json
{ "type": "search", "seq": 3, "moves": [112, 113, ...], "level": 4 }
```
`moves` 是完整着法序列（一维下标），Worker 重放后从当前局面搜索；
`level` 是档位号（module Worker 导入 `difficulty.js` 读取定义）。

**Worker → 主线程**
```json
{ "type": "ready" }
{ "type": "info",  "seq": 3, "depth": 6, "score": 12500, "nodes": 82341, "nps": 410000, "time": 201, "pv": [98, 113] }
{ "type": "result", "seq": 3, "move": 98, "score": 12500, "depth": 6, "nodes": 82341, "nps": 410000, "time": 205, "vcf": false, "forced": "none" }
```
`forced` 字段如实标注硬规则触发：`"win1"`（己方一步成五）/ `"block1"`
（对方一步成五）/ `"none"`。`vcf=true` 表示这步来自算杀。

`bridge.js` 负责自增 `seq` 配对、丢弃过期应答（用户连点/悔棋/重开必然产生
过期回复），并把 `info` 流转发给侧栏做实时深度显示。

## 8. GitHub Pages 部署约束

* **纯静态**：没有构建步骤、没有依赖安装、没有第三方库。所有代码手写并随仓库分发。
* **不需要 COOP/COEP**：引擎是普通 Web Worker，不依赖 SharedArrayBuffer。
* **`.nojekyll` 必须存在**：否则 Jekyll 会忽略以 `_` 开头的路径。
* **分发**：全部前端源码随仓库提供，可直接使用静态托管。
